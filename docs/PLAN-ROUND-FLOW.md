## 0. 两条底线（用户定，2026-08-08）

1. agent 必须知道自己在做角色扮演。
2. 一切为剧情、为用户的扮演体验服务——分段是为了让用户有上文可依、让戏不被固化；
   查库是为了世界在用户眼里不漂。手段都要说出目的。

## 1. 三个关键理解

### 1.1 分段的目的：给选择提供上文

分段不是工具纪律，是**交互设计**。用户要参与剧情、要做出选择，前提是手里有上文——
看到一段，知道这一拍演到哪了，才能说「我要往这边走」。一次交完，用户对着完整成品
抓瞎，选择无从谈起。

**每段之间天然存在一个用户介入点。** 这就是分段与 ask 的关系：分段是为 ask 服务的。

### 1.2 计划是假设，不是剧本

beat_plan 不是「列完 → 照单执行 → 勾完收笔」的执行流水线，而是**第一段的起点假设**。
它存在的唯一理由，是给「下一段演什么」一个初始答案。

每演完一段，上文就变了——模型和人一样，**有了新上文就必须重新思考原计划还合不合理**：

1. 演完一段 → 获得这一段带来的新上文
2. 重新评估：原计划剩余几步还成立吗？在上文已经变化的条件下，有没有更好的展开？
3. 成立 → 接着演；不成立 → 重拟 beat_plan（剩下的步重新写，不硬演早先的设想）

「已经写下的戏比计划更算数。」计划是服务于当前上文的临时决策，**剧情永远不被计划锁死**。
这就是分段的目的：不想让剧情固化。一次写完 = 剧情在落笔前就凝固；分段写 = 每一步都
在上文基础上重新活一遍。

### 1.3 ask 接入后：变化是常态，不是例外

ask 接回后，流程可变性是**根本属性**：

- 每段演完 → 用户看到段 → 可能主动接话、可能被 ask 提问
- 用户的回答 = 新上文 = 剧情改道 → **剩余计划当场作废，重拟**
- ask 不是「第 1 轮规划时」的一次性工具——**它是每段之间的常态介入点**：剧情要分岔了，
  停下来给用户 2~4 个选项；用户选了，计划跟着改，继续演。

用户参与选择之后剧情不可能一成不变——ask 的答案每来一次，后面的路就要重走一遍。

## 2. 三层分工（谁也别抢谁的活）

| 层 | 归属 | 职责 |
|---|---|---|
| **思考** | 演员 | 读题（本拍什么处境）、回看（刚写下的那段决定下一段）、评估计划。**不排练正文** |
| **稿纸** | 表演 | 正文唯一入口。一段一段落，落下去就算数 |
| **验收** | 机器 | 字数、禁词、格式、主权程序化判定，违规清单一并回喂 |

三个病根全是抢活：思考里排练（演员抢稿纸）、思考里算字数（演员抢机器）、
一次性交全文（跳过稿纸直接宣读）。

## 3. 一拍之内：按思考轮次的完整流程

### 输入基线（每拍开始前，模型手里已有）

- **常驻系统提示词**（会话内字节稳定）：`# 舞台` → `# 演出节拍` → `# 你扮演的角色` →
  `# 用户扮演` → `# 世界设定（常驻事实）` → `# 叙事与文风` → `# 输出结构` →
  `# 怎么演这一拍` → `# MCP 外设`（可选）→ `# 消息流约定` →
  预设拆层三节（A 原文 / B 文风 / C 边界）→ `# 卡作者附加指令`
- **每拍注入**：【世界状态】→【登场名录】→【活跃面板】→【相关设定】→【设定集索引】→
  【预设末端指令】→【文风与写法】→【行为边界】→【导演备注】
- **用户最新消息** + 历史正文

### 第 1 轮思考——探索与规划（规划轮）

**思考内容**（只许三件事）：读题（谁在场、上文到哪、用户要什么）→ 判型（有戏/没戏）→
构思（有戏则演哪几步）。

**可调用工具**：

| 工具 | 触发条件 | 后果 |
|---|---|---|
| `lorebook_search` | 要写没有十足把握的设定 | `lookups++` |
| `memory_search` | 要带回记不清的人/物/旧账 | `lookups++` |
| `world_state_get` | 拿不准时/地/关系 | `lookups++` |
| `writing_guide` | 预设 D/E 类方法论 | 不打点，结果随拍蒸发 |
| `beat_plan` | 构思完成，列 2~8 条路标（≤60 字/条） | 计划落清单 |

**结束条件**：`beat_plan` 被接受，回执「已记下计划（N 条）……按第一条未完成的写：
draft_append」。到这一行为止，**正文一个字都不许出现**——路标限长是结构性保证
（构思与排练的物理分界）。

**分支**：
- 没戏拍（寒暄/确认/应一声）→ 跳过规划，`draft_write` 一次交完（`lookups==0` 门禁放行）
- 查到的内容与计划冲突 → 重拟 beat_plan 再进入下一轮
- 命中「必须问」（接 ask 后）→ 第一个动作就是 ask，等用户拍板再列计划

### 演段轮循环（真·心脏）

```
演一段（draft_append）
  → 回看刚写的（新上文到手）
  → 评估原计划：还剩的几步还成立吗？
      ├─ 成立 → beat_step_done 勾掉刚演的这条，演下一条
      ├─ 不成立 → beat_plan 重拟剩下几步，按新的演
      └─ 剧情到岔路 → ask 用户 → 答案改道 → beat_plan 重拟 → 按新的演
```

每轮思考新增输入：beat_plan 清单回执（□/☑）+ 现稿 + 工具结果 + 验收报告（未封笔
**无字数读数**）。每轮思考内容：只围绕当前这一段；不看计划全貌、不想后面的段。

写到不确定处才停：查设定/回忆/账本（这时查 → `lookups++`）。

### 收尾轮

- **收笔条件是「戏自然演到停点」，不是「清单勾完」**——哪怕清单还剩两条，只要戏到了
  用户能接话的位置，就可以收
- 通读现稿（需要就 `draft_read` / `draft_search` 定位）
- `draft_seal` 封笔 → 全量验收（此刻才报字数）
- 有违规 → `draft_edit` 定点改（可多轮）→ 自动复验
- `world_state_update` 记账
- 全绿且账已记 → 停止调用 → 正文上屏，停在用户可接话处

### 兜底路径（模型走错时 harness 拉回主线）

- 直出正文 → 引擎代收为 `draft_write`（internal 旁路，不丢正文）
- 一直不落笔 → 催稿「你还没有落笔——用 draft_append 演一段…」
- 查过库却一次交全文 → `draft_write` 门禁拒收：「这拍查过 N 次世界，有戏，一段一段演」
- 思考宣告写尾巴（状态栏等）→ 收尾放行门控多给一轮

## 4. ask 工具接入规范（接回时执行）

旧 ask_director 语义（director.ts 决策门禁）：「必须问」三类——① 用户求方向/递笔
（「怎么办」「给个选项」）；② 用户要生成/定型身份（禁止代写完整档案）；③ 场景岔路
2+ 方向且影响后续多拍。判据：**此刻不定下来剧情就走不下去**（不是「新不新、重不重要」）。

接入位置——**每段之间的常态介入点，重点是规划轮**：

1. 第 1 轮读题命中「必须问」→ 第一个动作就 ask（不落笔、不先演），给 2~4 个具体、
   可落地、彼此不同的选项，等用户拍板
2. 用户回答作为新 user 消息回喂 → 重新构思 → beat_plan 按答案列路标 → 照常演
3. 身份生成：ask 拆成关键选项（出身/职业/性格基调/与主角关系），用户答完再演
4. 演段轮中剧情到岔路 → ask → 答案改道 → 剩余计划重拟 → 继续演
5. 回合末岔路：预设带选择框格式（如 `<w2g>`）时按格式写进正文收尾，不调 ask；
   预设没有选择框才用 ask 工具弹卡
6. ask 的结果改变了剧情输入，应计入「这一拍有戏」的事实（lookups 或单独打点，接回时定）

## 5. 任务流程的固定与可变

**固定不变的部分（骨架）**：演一段 → 评估 → 再演。寒暄例外（没戏拍直接交）。
这个顺序不因剧情而变。

**可变的部分（每轮的实际输入与分支）**：
- 读什么：取决于要写什么（设定/记忆/账本/方法论），查不到就模糊带过
- 计划几条：2~8 条，**每段之后都要重新评估，随时重拟**
- 中途分支：查库冲突 → 重规划；必须问 → 先 ask；没戏 → 跳过规划
- 打磨几轮：验收违规才 edit，绿了就停（不做无谓打磨）
- 兜底路径：直出代收、催稿、门禁拒收，全是模型走错时拉回主线

**流程的「固定」靠循环结构，不靠提示词写死步骤**——每轮的「干什么」由工件
（清单/现稿/报告）告诉模型，不由静态文字告诉。剧情永远不被计划锁死。

## 6. 与 opencode 源码机制的对照（2026-08-08 源码研究）

| opencode | 梨园对应物 | 状态 |
|---|---|---|
| plan agent（只读，物理上不能改文件） | 规划轮：只探索+列路标，路标限长 | 结构接近，缺「列完就停」的显式声明 |
| plan_exit 仪式 + build-switch 注入 | 「plan 已接受，开工」切换信号 | **缺失**，模型不知道自己身份已切换 |
| todowrite 存库、每轮回读 | beat_plan 清单随工具结果回传 | 已实现（未提交） |
| 只有真验证过才标 completed | beat_step_done 勾「已交出的段」 | 已实现（未提交） |
| plan-mode / build-switch 每轮动态注入 | 分轮提醒卡（注入层） | **缺失**，流程全在常驻层 |
| 子代理权限 deny | 演段轮不存在写侧以外的工具 | 已实现 |

opencode 与梨园方案几乎同构，但它多了一样梨园没有的东西：**「第 1 轮做完之后，身份
切换这个动作本身是仪式化的」**——plan_exit 要用户确认、build-switch 要注入提醒，模型
明确知道自己现在是什么身份、能干什么。梨园缺的就是这层「现在在第几步」的显式信号。

## 7. 梨园现有系统提示词的问题（对照最终形态）

**核心问题：流程全写在常驻层，注入层不存在。**

- opencode 的流程（plan-mode / build-switch）是每轮动态注入的；梨园把 beat_plan 循环
  写死在常驻系统提示词里，每轮一样。模型从静态段落里猜自己该干什么，而不是从注入
  状态里知道自己该干什么。
- 具体毛病：
  1. 开篇「始终思考剧情的发展和走向」把全貌思考合法化到每一轮（第 1 轮才准想全貌）
  2. 「然后按这个循环演出」把 2、3、4 轮压成一个箭头，模型一口气全干完
  3. 没有「列完清单就停、正文下一轮才开始」的轮次结束条件
  4. 没有身份切换仪式（规划者 → 演员）
  5. 【导演备注】是纪律大杂烩（语言/篇幅/停拍/状态栏/思考用法混在一起），
     一个提醒只办一件事的原则被违背
  6. 机械纪律（「不要在思考里逐条自查」）在四处重复出现，强调通货膨胀

## 8. 预设与提示词的关系（内容供给者 ↔ 流程执行者）

预设经拆层（PRESET-SPLIT-TAXONOMY）按九性质分五去向：A 破限/B 文风/C 边界 → 常驻；
D 方法论/E 场景包 → skill 按需（writing_guide）；F 机械纪律 → 代码；G 验算指令、
H 脑内 harness、I 死块 → 退场/蒸发。

**关系本质：预设 = 内容供给者，提示词 = 流程执行者。拆层把预设里的"机制"全删了
（H 类合计 ~14k 字：COT 系统、七步问题清单、草稿机制、思考≥3500 tokens 教唆），
流程只能由梨园提示词接棒——但梨园自己的流程提示词还没立住。这是「一点进展都没有」
的另一半原因：预设侧拆了，提示词侧没补。**

关系中的问题：
1. **双重真空**：预设的流程指令退场了，梨园的轮次流程又没接住
2. **B/C 常驻不绑轮次**：TGbreak ~2.5k、双人 ~5.2k 的文风+边界每轮在场，
   第 1 轮本该只探索列路标却背着 5k 字内容约束进场
3. **writing_guide「动笔前读」与第 1 轮冲突**：方法论是演段轮的粮食，却安排在规划轮，
   诱发第 1 轮构思人物细节；应改为「演到相关段落时读」
4. **注入层被预设内容占满**：每拍注入全是「内容」，没有给「你现在在第几步」的流程提醒
   留位置
5. **遗留**：A 类破限的 `{{random}}` 破坏前缀缓存（拆层文档 §4.5，未修）

| 层 | 内容 | 对应 opencode |

- `# 怎么演这一拍` 从常驻层搬走循环描述，改成流程总纲一句

- ask 接入位置：规划轮 + 每段之间的常态介入点

## 12. 8/08 晚二次修正：注入卡追不上连发，改硬件级门禁

## 13. 2026-09-09：临场维护与续演的归属

当前仍由原生 `AgentSession` 执行模型/工具循环。主模型可在该循环内切入写卡模式，开放已保存的完整操作历史与文件/卡资源工具；用户也可手动切换。返回扮演后，维护请求、代码与操作记录重新封闭，原剧情连续保留，卡片采用已应用的新内容。

写卡轮不执行剧情稿件收尾、场记、入库或剧情压缩；剧情视图、状态、摘要与记忆共用请求归属。退出维护结束当前运行，下一条用户输入才续演，避免把修改报告接成故事。隔离页面验证与官方 DeepSeek 基础修改/续演已通过，详见模式记录。

本次离最终流程更近之处，是用户可以在演出途中调整卡片或界面，再回到原剧情继续作出选择，维护操作不成为新的故事材料。此项不恢复上文历史记录中已撤销的强制检查、额外裁判或固定工具步骤。

## 14. 2026-11-22：下一拍开演前先追平状态账本

定稿后的场记仍属于前一拍收尾。若旁路失败，引擎把该拍文本和标识保存在当前会话分支；下一条剧情生成前，先按序重试待补拍。同步成功后，最新状态才进入下一拍的【世界状态】注入。同步再次失败时，本次输入不落树、剧情模型不启动，用户可修复旁路后重试。

旧会话若在最近状态快照后还有未标记的完成剧情拍，引擎最多回看最近 12 拍并补入待处理队列。没有任何状态快照的旧会话不自动扫描全历史；需要时仍可手动场记同步。分支回退只读取当前分支上的待补记录与状态快照。

本次让实际引擎流程更接近「下一拍读取当前世界」：不把旁路失败静默留到未来；先恢复前拍状态，再装配并调用剧情模型。代价是待补记账失败时暂停续演，避免模型继续使用已知陈旧状态。

## 15. 2026-11-22：手动恢复失败的场记

状态栏按当前会话分支展示持久化待补拍数量；「重新记账」只按序重放已有 `rp-scribe-pending`，不扫描近 12 拍、不创建新剧情。成功记录完成标记并收起提示；失败保留待补记录，下一拍仍受原门禁保护。

这让流程更接近「下一拍读取当前世界」：用户不必发送下一条剧情才能触发已存在的恢复流程，可先显式补齐上拍状态；同一叶守卫与按序写回继续生效。重试期间新输入先排队，补账释放引擎后再开演。

## 16. 2026-11-23：长局压缩与旁路输出边界复核

每个成功封笔的剧情拍先等待场记处理（成功时写回账本；失败时保留待补记录），`StageEngine.finish()` 随后按配置周期调用自动压缩。摘要只覆盖早期完成拍并保留最近 6 拍，提示从新覆盖的剧情正文判断语言。旁路沿用所选模型条目的 `maxTokens`；`stopReason=length` 作为失败返回，不落部分摘要或状态补丁。

这与「下一拍读取当前世界」一致：场记成功时新账本成为下一拍事实，失败时原有待补门禁阻止用旧账本开演；压缩只替换已被保留区覆盖的早期原文。`interval=1` 的引擎集成回归在第 7 个完成拍验证了该边界。

## 17. 2026-11-23：每拍把当前场景角色位置对齐到账本

场记提示要求据本轮正文判断已知角色是否物理身处当前场景并在现场行动/当面对话；若账本 `at` 缺失或与本轮 `location` 不同，就把在场角色的 `at` 写为当前地点。只有名字被提及、回忆、远程传讯，或角色明确身处别处，不据此改成在场；值已一致时不重复写入。

这让流程更接近「下一拍读取当前世界」：场记返回位置补丁时，修正后的 `at` 进入当前分支账本，供下一拍装配和状态面板读取。离线测试验证位置补丁后的状态计算，Chromium 验证手动修正所在地后名录更新；两者不保证模型每次遵循提示。原会话快照与完整模型回复不可用，无法复现 issue #21 中三名角色的具体旧位置。


## 18. 2026-11-23：用户确认的当前分支状态纠错

状态栏的「状态纠错 Agent」接收自然语言说明，只向旁路模型提供当前分支账本及最近最多 12 个完成剧情拍（正文截尾至 20,000 字符）。Agent 必须返回逐字可核验的指令/剧情引文和受限字段补丁；证据无效、内容含歧义、输出越权或无法解析时只显示澄清/失败，不写入。面板先展示证据与改前/改后，用户明确确认后服务端才应用服务端持有的提案，客户端不能提交替代补丁。尚未进入分支账本的卡初始 MVU 树不会仅因提案而被隐式写入；MVU 修复只作用于账本中已有的变量树。

提案绑定会话、分支叶和原账本。若当前分支尚无状态快照，仅当整棵会话树都没有任何 `rp-state` 条目时，旧会话/导入账本的磁盘缓存才可作为基线；若 sibling 已有快照而当前分支没有，则使用默认账本，不继承共享缓存，避免重生成后复活废弃分支。状态栏读取与扩展启动恢复遵循同一规则。确认前任何一项变化都会使提案失效；确认后单个 `rp-state` 快照携带账本和保留的 `__stateRepair` 审计元数据（用户指令、补丁、证据、修复前状态），避免快照和审计分裂。SessionManager 的 append/flush 失败会回滚本次内存索引和活动叶节点，不广播或同步未提交状态。读取账本时剥除审计元数据。磁盘仅作缓存；分支快照提交后扩展内存立即同步，服务端直接广播当前分支账本，缓存写失败仍返回已提交并向用户警告。下一拍装配仍从当前分支最新可见状态快照读取，不会改写故事正文；旧写作分支若会过滤新状态快照，提案在送模前拒绝。撤销凭据绑定会话、分支叶和具体修复快照；请求凭据与服务器当前可撤销修复不匹配即拒绝，撤销以单个带 `undoOf` 的 `rp-state` 快照记录，不可重复翻转；后续状态写入会阻止覆盖。续接会话时以当前可见分支快照恢复，用户手动编辑也以分支快照优先，避免旧缓存复活已修正事实。

这是让「下一拍读取当前世界」更可靠的人工纠错通道，不是事实验证器：模型只能在提供的 12 拍/20,000 字符窗口内引用文本，不能证明用户指令真实，也不能从窗口外历史验证事实。证据引文精确匹配可阻止虚构引文，但不能保证解释正确；用户须核对预览。分支切换、状态变化和后续状态写入均优先于提案/撤销。

## 19. 2026-11-23：独立的多轮状态修改会话

状态修改对话按具体扮演会话持久化，支持新建、续聊和删除；不同会话互不共享，删除扮演会话时级联删除其状态修改记录。每次创建、删除、续聊或应用请求都必须带上客户端当前持有的扮演会话 ID，服务端与实时当前会话不匹配就拒绝，避免切换期间的迟到请求写入新会话。每轮把用户/助手历史一并交给 Agent，提案仍须逐字证据校验并绑定发起它的修改会话、扮演会话、分支叶和账本版本；只有该修改会话中的提案 token 可以确认应用。发送、续聊或离开工作区均不应用提案；旧提案历史仅供回看，绑定条件不再满足时仍由既有分支/账本守卫拒绝。

进入或刷新时不创建修改会话；选择「新建修改会话」只打开空白对话，首次发送时创建会话并提交消息。标题栏的会话列表首项固定为「新建修改会话」，其后列出已有会话；每条已有会话可行内重命名，回车保存、Esc 或失焦取消，标题随所属扮演会话持久化。列表在标题分割线下方覆盖对话，不推动对话，超过高度限制时在列表内滚动。

发送后立即显示用户气泡；模型真实返回的思考和回复增量在工作区显示，思考支持折叠。提案成功写入后标为「已应用」，不再重复应用，标记随修改会话保存。下一拍仍读取确认写入的当前分支状态，而非流式过程或未确认提案。

状态问答读取当前分支账本，可直接返回只读回答并保存到修改对话；不要求逐字证据，也不生成或应用补丁。提示词要求按本轮及上下文区分问答与修改，修改请求输出实际补丁或澄清，不能只用文字声称有提案；模型仍可能误判，服务端对只读回答明确标注未生成提案。回答与补丁不能混在同一输出中；修改仍须校验证据并经用户确认。问答不会改变下一拍读取的分支状态。

MVU 和数据面板修正的路径以各自现有变量树为根；提示词用通用示例说明路径格式，不假定角色卡字段。程序继续校验字段存在、安全路径和逐字依据，确认前不写账本；确认后的状态才供下一拍读取。

`repairModel` 在模型详情中像旁路和助手模型一样指定或取消；为空时跟随当前剧情主模型，选择模型条目后必须使用该条目，无法解析或鉴权时明确报错而不回落。状态修改提示词与助手提示词一样，在「提示词 → 全局系统提示词」中按 `REPAIR_APPEND_SYSTEM.md` 的条目编辑和开关；模型只读取启用条目。旧 `repairPrompt` 内容迁入文件；可配置条目不改变程序内置的状态范围、证据校验或确认应用边界。

旧模板开头没有正文的「状态修改工作方式」标题在启动时清除；同名标题已有正文时保留。其余规则与下一拍读取当前分支状态的流程不变。

确认后的修改仍以当前分支 `rp-state` 快照进入下一拍装配；多轮澄清与差异预览让用户在写入前核对依据，减少下一拍沿用错误账本的风险。证据匹配只验证引文存在，不代替用户判断事实和解释。
